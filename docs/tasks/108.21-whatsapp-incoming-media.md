# Step 108.21 — Safe incoming attachment metadata and inbox cards

Implement image/document/audio webhook validation, bounded metadata retention and safe inbox cards using existing scoped durable transactions. Do not download, render, play, transcribe, send or claim file verification. Existing text, claims, approval and status behavior must remain compatible.

## Dependencies and gates

- The existing message JSON constraint permits no extra fields. Prepare an additive nullable `media_metadata` column and strict check; do not relax existing record constraints, RLS, grants, triggers or audit requirements.
- SQL remains review-only. No new SQL execution, infrastructure, live workflow changes or deployment is authorized by "continue".
- Keep legacy text-only connector schemas unchanged; extend only the durable webhook surface. Provider fields remain untrusted; retain selected bounded fields only. No URLs, tokens or raw provider metadata enter the inbox.
- Metadata references are not file retention or authenticity proof. Downloads require a future authorized adapter, byte limits, MIME verification, malware checks and protected storage. Templates/outbound media are separate unfinished work.

## Acceptance

- Text compatibility, image/document/audio normalization, filename/caption sanitization, sender/asset/tenant rejection, atomic mixed-batch failure, duplicate/conflicting media IDs, audit rollback.
- Append-only metadata persistence shares existing row RLS/audit and preserves old text rows; prepare runtime acceptance for isolated SQL and restart persistence without executing new migrations.
- Browser contracts reject extra metadata/URLs; attachment cards cannot fetch or execute media. Surface "Not downloaded" honestly.
- Focused tests and builds; record unexecuted SQL/runtime gates explicitly before requesting consolidated authorization.
