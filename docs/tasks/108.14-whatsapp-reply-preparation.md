# Step 108.14 — WhatsApp reply preparation in the Thaara app (sending disabled)

Same WhatsApp master task, after the first real inbound message (108.13b).

## Delivered (local code, not yet deployed to the VPS pilot)

- **API** `POST /api/v1/connectors/whatsapp/n8n/durable/:connectionId/reply-drafts` (owner session + CSRF, no-store). The server builds the `whatsapp.meta.messages.send` draft from the connection binding (connection ID, revision, sender phone number ID), so the browser never supplies Meta IDs. It accepts only an opted-in recipient. `replyToProviderMessageId` must be a stored message in that same conversation. Relay callers and viewers are refused. No state change, no audit, no transport.
- **Contracts:** `N8nWhatsAppReplyDraftRequestSchema`, `N8nWhatsAppReplyDraftSchema`, `isN8nWhatsAppReplyDraft`, `isN8nWhatsAppReceipt`.
- **Web (stored inbox):** a "Prepare a reply" box for the selected conversation. Flow: server draft → `POST /api/v1/approvals` (high risk, 1 h) → a separate **Approve reply** click → `decide` → existing durable `reserve`. The result is shown as "Prepared, not sent" with "Nothing was sent to WhatsApp". It fails closed on any invalid response, and switching conversation discards a pending reply.
- **Safety check:** the generic approvals endpoint executes only plan-step-bound actions, and there is no WhatsApp send adapter, so approval cannot send. Reserve re-validates the approval hash, binding, revision and opt-in server-side.
