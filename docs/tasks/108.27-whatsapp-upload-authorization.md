# Step108.27 — Explicit upload authorization and durable replay protection

Local-only continuation; no provider calls, infrastructure, migrations, remote workflows, credentials, deployment, sends or commits. Preserve108.26 and all prior work.

## Design and dependencies

Uploading bytes to Meta is an external write distinct from sending a message. Use a registered typed `whatsapp.meta.media.upload` action with explicit approval bound to connection revision, sender, exact size/type/name/SHA-256 and idempotency key. File selection/preparation creates only an unsent upload authorization. The owner explicitly approves transfer, then separately approves the resulting message draft. No automatic approval.

Reuse existing scoped approval, idempotency and audit tables; no new SQL. Commit a one-use admission and audit before external transfer. Serialize claims by approval, reject changed payload/scope, never retry an ambiguous/failed transfer automatically, cache only a confirmed uploaded result after authorization rechecks. Recheck membership, session, binding revision and approval around transfer. Audit/admission failure must prevent provider I/O.

The existing generic approval route applies an unconditional high-risk two-person rule even to the registered explicit WhatsApp send action. Add a narrowly scoped personal WhatsApp decision path, validated against the registry, exact requestor and current owned binding; retain two-person behavior for all other actions.

## Acceptance

- Missing/foreign/expired/changed approvals, stale binding/session/role and policy denial => zero provider calls.
- Admission/audit failure => zero provider calls; concurrent/replayed authorization => at most one transfer; restart/unknown outcome never silently retried.
- Upload result/audit failure and disconnect after transfer return no false success. No credentials, file bytes or provider diagnostics in errors/audits.
- Browser shows separate upload and send approvals and fences async navigation. Focused tests + meaningful integration/build checks; actual PostgreSQL verification uses only already authorized existing in-memory fixtures, not new external infrastructure/SQL.
