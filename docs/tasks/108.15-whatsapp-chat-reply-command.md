# Step 108.15 — WhatsApp reply command in Thaara Chat (sending disabled)

Same WhatsApp master task, after 108.14 (inbox reply preparation).

## Delivered (local code, not yet deployed to the VPS pilot)

- `apps/api/src/services/chat-whatsapp-assistant.ts`
  - `detectWhatsAppReplyChatRequest`. Explicit command forms only:
    - English: "reply on WhatsApp: …", "WhatsApp reply: …"
    - Kanglish: "whatsapp alli reply madu: …"
    - Kannada: "ವಾಟ್ಸಾಪ್‌ನಲ್ಲಿ ಉತ್ತರಿಸು: …"
    - Questions and ordinary mentions of WhatsApp are ignored.
  - `executeChatWhatsAppReply`. Uses the owner's single connected inbox and single conversation, otherwise answers "ambiguous" and points to the inbox screen. It builds the draft through the durable `replyDraft` (server-built, replying to the latest inbound message), then creates a **governed plan**: one `whatsapp.meta.messages.send` step (high risk), a bound approval (1 h), and a `whatsapp.chat.reply_prepared` audit event. It does a fresh membership check, and refusal messages always say "Nothing was sent".
  - `createWhatsAppReserveAdapter`. On approval it calls the durable `reserve` for the exact approved draft and reports `unverified` with proof `{ reserved: true, sent: false, transport: 'not_configured' }`. It fails closed without an owner session scope or approval context.
- **Wiring:**
  - `conversations.ts` checks the WhatsApp reply command before Gmail. It reuses the governed plan/approval token shape, so the existing chat approval controls apply.
  - `approvals.ts` registers the reserve-only adapter for chat-orchestrated plans.
  - `app.ts` shares one `DurableWhatsAppService` across them.

## Evidence

- Unit tests 16/16: detection in English, Kanglish and Kannada; negatives; not-configured, ambiguous and denied branches with no database writes; the adapter's reserve and fail-closed cases.
- Real PostgreSQL harness 7/7. The 108.15 case: ambiguous with three inboxes; after disconnecting two, it creates a plan, a step and a pending high-risk approval with its binding, and 0 dispatches. After approval, the adapter reserves exactly 1 unclaimed dispatch, `sent:false`.
- Regression: 342/342 across 25 files (conversations, chat, Gmail, Calendar, approvals, plans, WhatsApp, web inbox). API typecheck is clean.

## Not verified / next

- It isn't deployed to the pilot (that needs a new image, hosted UI and login approval).

- Sending stays disabled until the claim/receipt principal, the outgoing workflow, a window check, and explicit owner approval of one controlled test.
