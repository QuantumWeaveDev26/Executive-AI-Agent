## Implemented

- Separate shared Meta test configuration, exact recipient/send binding, official-shaped message/status envelope and offline receipt schemas. Existing mock contracts are unchanged.
- Separate high-risk whatsapp.meta.messages.send action with explicit approval, workspace/requester and exact parameter binding, idempotency, audit and zero automatic retries. No runtime action adapter is registered.
- Server-only MetaWhatsAppTestFoundation: disabled by default and rejects configured construction outside NODE_ENV=test. It is not imported by buildApp, existing WhatsApp routes, UI or Chat. No environment variables, public callback routes or HTTP/fetch transport were added.
- Reused WhatsAppVault AES-256-GCM with workspace/user AAD and separate connection/revision purpose; no plaintext credential fields retained by the provider. Caller supplies synthetic secrets only through explicit test injection. Deployment must use the existing managed-secret/KMS abstractions plus a separately approved persistent connector store; this step does not configure durable storage.
- GET challenge helper uses a distinct verify token; POST helper validates HMAC-SHA256 with the app secret over a copied raw Buffer before JSON parsing. Generic errors and audit allowlists omit secrets, recipients, bodies and raw provider errors.
- All WABA/phone IDs must match the trusted server binding; payload-supplied tenant/user claims are rejected. Unknown test recipients, oversized/malformed/deep payloads, old/future event timestamps and mixed-asset batches fail closed. Duplicates are suppressed atomically within the bounded temporary test inbox. Incoming text is sanitized, labelled untrusted and never interpreted as instructions.
- A text/reply descriptor uses the official versioned https://graph.facebook.com/{reviewed-version}/{phone-number-id}/messages endpoint. Meta test numbers use the same Cloud API, not an invented sandbox URL. Configuration requires an explicitly reviewed Graph version allowlist; there is no default version. v26.0 in tests is a structural fixture, not a claim of account eligibility or a verified current-version choice.
- Recipient IDs resolve exclusively through the server allowlist with E.164 validation, recorded opt-in, sender/revision matching, same-recipient reply context and an actual received-message timestamp within 24 hours. No template capability is faked. prepareSend cannot send: even approved attempts return not_configured / sending_disabled, no provider message ID and verified=false.
- Acknowledgements remain unverified. Synthetic status reduction requires message/recipient correlation, avoids status regression and always preserves mode=offline_test/verified=false. Unsolicited delivery webhooks do not create outbound receipts.
- Disconnect immediately fences pending work, removes ciphertext and clears temporary state before any fallible audit await. Per-request authorization is rechecked around async operations and on each duplicate waiter; audit failure cannot be bypassed through retry/idempotency.
