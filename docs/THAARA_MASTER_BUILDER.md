## 1. Product vision

**USER GIVES A COMMAND → THAARA PLANS → BUILDS → TESTS → SHOWS THE WORKING RESULT.**

Thaara should understand a person's intent through natural chat or voice, turn it into an explicit plan, carry out authorized work, test the outcome and present a usable deliverable. It should support executive assistance, communication, research, productivity, software building and business automation through one secure application.

The experience should combine ChatGPT-style conversation, natural multilingual voice and a practical builder that produces working websites, applications, documents and workflows. For consequential actions, the operating loop includes explicit review and approval before execution. The model proposes; deterministic services authorize and execute.

**Future agent orchestration framework:** use the official OpenAI Agents SDK for TypeScript where it fits Thaara's existing application. A Main Thaara Agent coordinates bounded specialist agents through governed tools and handoffs. The SDK runs AI orchestration; Thaara retains mandatory control of authentication, tenant isolation, PolicyGateway, approvals, audit, idempotency and verified outcomes. This is a planned integration, not an installed or enabled capability.

Thaara should speak naturally in English, Kannada and Kanglish, remember context with consent, admit uncertainty, show progress and explain blockers. A mock, generated draft, provider acknowledgement or attractive screen must never become a claim that real work succeeded.

### Product principles

1. Continue the existing V2 application. Preserve working Gmail, Calendar, Chat, dashboard, policy, approval, audit and tenant boundaries.
2. Build incrementally through one bounded task under `docs/tasks/` at a time.
3. Make results inspectable: source files, citations, previews, test evidence and verified receipts as appropriate.
4. Keep user control over recipients, spending, sensitive data, publication, permissions and irreversible actions.
5. Share backend intelligence and contracts across the web application and future mobile clients.
6. Show truthful partial completion and failure instead of hiding incomplete work.

### Scope boundaries

This is an extension of the existing pnpm/TypeScript monorepo, never a rebuild from zero. The legacy repository at `D:\thaara-ai-platform` remains reference material only; never copy its code, secrets, databases, `.env` files or unverified provider behavior. Recruiting/Talent OS is outside the existing architecture's scope unless separately requested.

This specification does not select new paid providers, promise unrestricted WhatsApp access, authorize autonomous external sending or guarantee background listening on every device. Provider eligibility, supported platforms, cost limits and deployment choices need task-specific decisions before their implementation.

## 6. Functional product requirements

### MB-01 — Intelligent AI Chat and conversation history

Provide a large, responsive ChatGPT-style conversation surface with streaming answers, follow-up context, clear error/reconnect states and automatic scrolling that respects users reading earlier messages. Keep conversation history on a separate page, with create/open/search/rename/delete/archive capabilities introduced only with backend support and privacy rules. Remove unnecessary headings and View Conversation controls as specified by the handover.

Reuse existing conversation, model/context, memory, SSE and auth services. Distinguish conversational answers, draft artifacts and executable plans. Missing model configuration must be visible. Memory is consented, reviewable and deletable; history is never shared across tenants or private owners by accident.

**Acceptance:** existing conversations remain accessible; streaming/reconnect/cancel and history isolation pass focused tests; a user can resume a conversation from History without duplicate execution; empty/error states are truthful.

### MB-02 — Natural real-time voice with interruptions

Support a user-started voice session with microphone permission, listening/speaking indicators, live transcript, natural turn-taking, optional text fallback and immediate stop/mute. Support barge-in: user speech stops playback promptly and invalidates obsolete response generation. A cancelled voice turn must not leave a pending unauthorized tool action running.

Voice must share Chat context and the same policy/approval path. Use short-lived server-authorized sessions; keep provider credentials off the client. Handle noise, silence, device changes, network loss, echo and reconnect without duplicate actions. Voice output must describe actual completion states.

**Acceptance:** measured first-audio and interruption-stop latency on named devices/networks; tested reconnect/cancel behavior; unauthorized/expired sessions denied; voice and text produce the same approval requirements. Set quantitative latency targets after a bounded provider/device evaluation rather than claiming unmeasured performance.

### MB-03 — “Hey Thaara” voice activation

Offer explicit opt-in wake-word listening with visible status, pause/disable controls and a clear supported-device matrix. Prefer local wake-word detection where practical; any upload before activation needs explicit disclosure/consent. Wake-word detection opens a session; it never approves a consequential action.

Begin with a supported foreground web experience and manual voice fallback. Background/locked-screen support requires separate OS/browser feasibility and battery/privacy evaluation; do not promise universal always-on listening.

**Acceptance:** documented microphone lifecycle, false-positive/missed-activation measurements, opt-out stops capture, no accidental call/send triggered by a wake word, truthful unavailable/background states.

### MB-04 — Kannada, English and Kanglish

Support Kannada script, English and Romanized Kannada/Kanglish in typed messages, recognition, generated speech and code-switched conversation. Respect explicit script/language preferences across turns while allowing changes. Use natural, concise phrasing rather than forced translations or repeated executive coaching during casual conversation.

Names, addresses, dates, amounts and contact identities require special accuracy. Confirm critical uncertainty before action; spoken Kannada does not imply that the user wants Kannada-script text. Preserve original source wording where a translated summary could lose meaning.

**Acceptance:** a bilingual human-reviewed evaluation set covers casual chat, tasks, mixed-language commands, contacts/numbers, interruptions and summaries. Record recognition errors, task accuracy and naturalness separately for each language mode; no claim of full voice support based on text prompts alone.

### MB-05 — AI phone assistant

Target command: **“Hey Thaara, call Ram, speak with him, then tell me what he said.”**

1. Resolve Ram through authorized contact data. Disambiguate similar names and confirm the intended number; never infer identity from untrusted message text.
2. Draft a bounded call brief: purpose, questions, permitted information, requested language, duration/cost ceiling and limits on commitments.
3. Obtain explicit approval bound to recipient, purpose, disclosure, script constraints and any separate recording/transcription consent. Voice confirmations must be unambiguous and backed by the same approval record; use visual review or step-up where policy requires it.
4. Place a call through an approved telephony adapter. Disclose that Thaara is an AI assistant acting for the user. Respect refusal, end-call requests, applicable calling rules and consent requirements determined before the pilot.
5. Converse naturally in Kannada, English or Kanglish, within the approved brief. Do not impersonate the user, reveal unrelated private information or negotiate unauthorized commitments. Escalate material changes back to the user.
6. Verify the call lifecycle with authenticated, correlated provider evidence. Busy/no-answer/failed/disconnected/uncertain calls must remain distinct from a completed conversation.
7. Provide an accurate written summary and optional spoken report: what was said, decisions, unresolved questions and follow-up proposals. Cite transcript segments/timestamps where available and consented. Mark unclear audio or uncertain speaker attribution; never invent a conversation when no usable evidence exists.

Recording, transcription and retention require explicit product/security decisions before enabling them; the current mock restrictions stay intact until separately implemented. Scheduling, messaging or purchasing mentioned during a call requires a new authorized action, not implicit permission from the callee.

**Acceptance:** controlled consenting test recipients; language/interruptions/disclosure tests; refusal and no-answer handling; scoped callbacks and duplicate protection; evidence-based summaries evaluated against consented call evidence; truthful receipt and cost accounting. Live calls need separate explicit authorization.

### 7.3 Orchestration, tools and mandatory enforcement

Prefer Main-agent coordination with specialists as bounded tools when Main should assemble the final result. Support explicit handoffs when a specialist should own a conversation branch, including language/voice transitions. The official [orchestration guide](https://developers.openai.com/api/docs/guides/agents/orchestration) distinguishes these patterns. Handoffs transfer AI work, never authority; carry filtered history and server-issued task references, not credentials or model-supplied roles.

The required execution route is:

`authenticated request → server-derived scope → agent proposal → shared-contract validation → PolicyGateway + application approval/audit/idempotency lifecycle → existing service/worker/adapter → outcome verification → agent report`

All SDK function tools, nested agent tools, handoffs, voice tools and any future MCP/hosted tools must use that route for protected operations. Tools cannot expose unrestricted provider clients, shell execution, raw SQL, secrets or arbitrary HTTP endpoints. The server selects permitted tool catalogs; model output cannot add capabilities. Validate SDK arguments against the canonical TypeBox/shared contracts before services execute. Review any SDK schema conversion/peer dependency requirements without replacing shared contracts or introducing competing public schemas.

Complex tasks follow **Plan → Execute → Verify → Report** using existing plans, dependencies, approvals, leases and receipts. Persist concise plans and action/evidence references; private model reasoning stays internal. The model can propose the next step but deterministic services decide whether it may run. A final SDK answer or successful agent run does not mark a plan/receipt verified. When approval is required, expose `awaiting_approval`, persist the continuation and wait; a free-text “approved” claim or SDK resume token is insufficient authorization.

On continuation, re-authenticate/recheck membership, approval expiry/revocation, canonical parameters, connector revision and budget. Tool-call IDs alone are not cross-run idempotency keys. Use durable action/plan identifiers; never execute the same mutation through both an SDK tool and the existing worker. Reconcile uncertain outcomes before retry, fallback or replay. SDK failure must not trigger a second send/call on the legacy path.
